# Архитектура LedgerCore: разбор по модулям

Цель этого документа — чтобы вы могли **объяснить** систему на собеседовании, не заучивая синтаксис C#. Для каждого важного модуля разобрано:

1. какую проблему он решает;
2. зачем он нужен;
3. что происходит по шагам;
4. какие конструкции C# используются;
5. аналог в TypeScript;
6. что сломается, если его убрать;
7. какие вопросы задаст техлид.

Пути к файлам даны от корня репозитория. Синтаксис подробно разобран в [CSHARP_SYNTAX_MAP_RU.md](CSHARP_SYNTAX_MAP_RU.md), путь одного запроса — в [REQUEST_FLOW_RU.md](REQUEST_FLOW_RU.md).

## 0. Общая картина за одну минуту

```
HTTP → Api → Application → Domain
               ↑ (интерфейсы)
         Infrastructure → PostgreSQL ← Worker
```

* **Domain** — «чистая бухгалтерия»: деньги, проводки, правила. Не знает ни про HTTP, ни про базу. Аналог в TS — модуль из чистых функций без `fetch` и `prisma`.
* **Application** — сценарии (use cases): «перевести деньги», «развернуть перевод». Описывает *что* делать и в каком порядке, но не *как* писать SQL.
* **Infrastructure** — *как*: SQL-запросы, блокировки, EF Core, миграции, outbox.
* **Api** — HTTP: токены, роли, rate limiting, коды ошибок.
* **Worker** — фоновые процессы: доставка outbox, чистка старых ключей идемпотентности, сверка балансов.

Главная мысль: **все гарантии живут в PostgreSQL** — транзакции, блокировки строк, уникальные ключи, триггеры. Несколько экземпляров API не делят между собой ничего, кроме базы, поэтому `lock` в C# здесь бесполезен.

## 1. Domain: деньги и проводки

**Файлы:** `src/LedgerCore.Domain/Monetary/Money.cs`, `Ledger/JournalEntry.cs`, `Ledger/LedgerRules.cs`, `Ledger/ChartOfAccounts.cs`.

1. **Проблема:** нужно гарантировать, что любая проводка сбалансирована, суммы положительны, а с кошелька нельзя уйти в минус.
2. **Зачем отдельный слой:** эти правила проверяются юнит-тестами за миллисекунды (68 тестов), без базы. Если правило сформулировано в одном месте, его нельзя «забыть» в каком-то эндпоинте.
3. **По шагам:**
   * `Money.CreatePositive(80000, Currency.Nok)` возвращает либо `Money`, либо ошибку `INVALID_AMOUNT`. Деньги — это `long` в эре; `double` не используется нигде.
   * `LedgerRules.PlanTransfer(...)` получает **уже заблокированные** снимки кошельков и проверяет: не перевод ли самому себе, владелец ли отправитель, активны ли кошельки, совпадает ли валюта, хватает ли денег. После этого строит `JournalEntry` с двумя проводками: Debit отправителю, Credit получателю.
   * `JournalEntry.Create(...)` отказывается создавать запись, в которой меньше двух проводок или Σдебет ≠ Σкредит.
   * `CalculateBalanceChanges(...)` считает новые балансы с `checked`-арифметикой: при переполнении будет ошибка, а не «перескок» через `long.MaxValue`.
4. **C#:** `sealed record`, `Result<T>`, `switch`-выражения, `checked`, статические методы, `readonly record struct` для ID.
5. **TS-аналог:** `type Result<T> = { ok: true; value: T } | { ok: false; error: LedgerError }`; брендированные типы `type WalletId = string & { __brand: 'WalletId' }` — это и есть наши `WalletId`/`CustomerId`.
6. **Если убрать:** правила размажутся по сервисам и контроллерам, и где-нибудь проверку забудут. Двойная запись перестанет гарантироваться кодом, останутся только триггеры базы.
7. **Вопросы техлида:**
   * *Почему кошелёк — это пассив (liability)?* Деньги клиента — это долг системы перед клиентом: кредит увеличивает долг, дебет уменьшает.
   * *Откуда берутся деньги при пополнении?* Из счёта расходов `5900-SIM-FUNDING-NOK`: Debit расход, Credit кошелёк. Запись сбалансирована, деньги «из воздуха» не появляются.
   * *Почему `long`, а не `decimal`?* Целые копейки (эре) исключают ошибки округления и смешение масштабов.

## 2. Application: сценарий перевода и идемпотентность

**Файлы:** `src/LedgerCore.Application/Transfers/TransferService.cs`, `Idempotency/IdempotentCommandExecutor.cs`, `Idempotency/IdempotencyTypes.cs`, `Security/CallerContext.cs`, `Abstractions/ILedgerTransaction.cs`.

1. **Проблема:** выполнить 13 шагов перевода в правильном порядке и ровно один раз, даже при повторных запросах.
2. **Зачем:** `TransferService` читается как нумерованный алгоритм из ТЗ (шаги подписаны в комментариях). Он не содержит SQL, поэтому его легко объяснить.
3. **По шагам** (`TransferService.CreateCoreAsync`, строка ~82):
   1. Проверить, что вызывающий — клиент (`caller.IsCustomer`).
   2. Валидировать ввод (`Validate`).
   3. Авторизация: кошелёк-источник принадлежит вызывающему (`WalletAccessPolicy.CanDebit`). Владелец кошелька никогда не меняется, поэтому эта проверка до транзакции безопасна.
   4. Посчитать «отпечаток» запроса (`RequestFingerprint`, SHA-256).
   5. `executor.ExecuteAsync(...)` открывает транзакцию → **первым делом** занимает ключ идемпотентности → выполняет `ExecuteLockedAsync` → сохраняет результат на ключе → коммит.
4. **C#:** primary constructor (`class TransferService(IdempotentCommandExecutor executor, ...)`), `async/await`, лямбды `(tx, ct) => ...`, локальная функция `RejectAsync`, `sealed record` для команд и ответов.
5. **TS-аналог:** сервис NestJS, которому через DI приходят зависимости; `executor.ExecuteAsync` похож на `prisma.$transaction(async (tx) => {...})`, только ключ идемпотентности занимается внутри той же транзакции.
6. **Если убрать `IdempotentCommandExecutor`:** повтор запроса создаст второй перевод. Это проверено мутацией: если игнорировать ключ, падают 10 тестов.
7. **Вопросы техлида:**
   * *Почему ключ проверяется внутри транзакции, а не до неё?* Проверка «до» — это гонка: два дубликата одновременно увидят «ключа нет». `INSERT … ON CONFLICT` по первичному ключу внутри транзакции заставляет второй дубликат **ждать** первого.
   * *Почему сохраняются отказы (`INSUFFICIENT_FUNDS`)?* «Тот же ключ + тот же запрос = тот же результат». Иначе после пополнения повтор по старому ключу вдруг пройдёт.
   * *Что такое `CallerContext`?* Это кто вызывает (subject, роли, correlation id). Application никогда не читает HTTP-заголовки напрямую.

## 3. Infrastructure: транзакция, блокировки, SQL

**Файлы:** `src/LedgerCore.Infrastructure/Ledger/NpgsqlLedgerTransactionRunner.cs`, `Ledger/NpgsqlLedgerTransaction.cs`, `Ledger/TransientFailures.cs`.

1. **Проблема:** два одновременных запроса не должны оба потратить один и тот же баланс, а любой сбой не должен оставить «половину» перевода.
2. **Зачем:** здесь живёт весь SQL денежного пути — его видно и его можно проверить на ревью.
3. **По шагам:**
   * `ExecuteOnceAsync` (Runner, строка ~63): открыть соединение → `BEGIN` (READ COMMITTED) → `SET LOCAL lock_timeout = 5s` → выполнить работу → checkpoint `BeforeCommit` → `COMMIT` → checkpoint `AfterCommit`. `await using var transaction` гарантирует ROLLBACK при любом исключении.
   * `ExecuteAsync` (Runner, строка ~22): при deadlock (`40P01`), serialization failure (`40001`) или потере соединения **повторяет всю транзакцию**, до 4 попыток с экспоненциальной задержкой и jitter. Повтор безопасен благодаря идемпотентности.
   * `LockAccountsAsync` (строка ~89): **один** запрос `SELECT … FROM ledger_accounts WHERE id = ANY(@ids) ORDER BY id FOR UPDATE`. Все транзакции берут блокировки в одном и том же порядке, поэтому deadlock между ними невозможен.
   * `ApplyBalanceChangesAsync` (строка ~212): `UPDATE … SET balance_minor = balance_minor + @delta … RETURNING balance_minor`, затем сравнение с ожиданием из домена. При расхождении — исключение и откат.
4. **C#:** `await using`, `catch (...) when (...)` (фильтры исключений), `switch`-выражение с паттернами `PostgresException { SqlState: ... }`, raw string literals `"""…"""` для SQL, `NpgsqlParameter` для всех значений.
5. **TS-аналог:** `pg` + `client.query('SELECT … FOR UPDATE', [ids])` внутри `BEGIN/COMMIT`; `await using` ≈ `try { … } finally { await client.release() }`.
6. **Если убрать `FOR UPDATE`:** оба запроса увидят 1000 NOK, и второй получит 500 (сработает CHECK-ограничение) вместо аккуратного 422. Проверено мутацией: падают 6 тестов конкурентности. Если же кто-то напишет `SET balance = @новоеЗначение` без блокировки, деньги создаются из воздуха — это показывает `LostUpdateDemonstrationTests`.
7. **Вопросы техлида:**
   * *Почему READ COMMITTED, а не SERIALIZABLE?* Корректность обеспечивают явные блокировки ровно нужных строк. SERIALIZABLE тоже корректен, но под нагрузкой откатывает транзакции при COMMIT, и их приходится повторять. С блокировками получается упорядоченная очередь (ADR-0003).
   * *Что будет, если deadlock всё-таки случится?* PostgreSQL прервёт одну транзакцию (`40P01`), runner её повторит, а метрика `ledgercore.db.transaction.retries{reason=40P01}` это покажет. В тестах и нагрузочном прогоне таких повторов было 0.

## 4. Миграции и триггеры: вторая линия обороны

**Файлы:** `src/LedgerCore.Infrastructure/Persistence/ModelConfiguration.cs`, `Persistence/Migrations/20261014212958_LedgerIntegrityRules.cs`.

1. **Проблема:** что если в C#-коде баг или кто-то пишет в базу напрямую?
2. **Зачем:** база сама соблюдает инварианты независимо от приложения.
3. **Что именно:**
   * `CHECK (allow_negative_balance OR balance_minor >= 0)` — баланс кошелька не может стать отрицательным.
   * Составные внешние ключи `(account_id, currency)`: валюта проводки совпадает с валютой счёта и записи.
   * Отложенные (`DEFERRABLE INITIALLY DEFERRED`) триггеры: при COMMIT каждая запись должна быть сбалансирована и иметь ≥ 2 проводок.
   * Триггеры append-only: `UPDATE/DELETE/TRUNCATE` истории запрещены.
   * Ключ идемпотентности нельзя закоммитить без сохранённого результата.
4. **C#:** EF Core Fluent API (`b.ToTable(..., t => t.HasCheckConstraint(...))`, `HasAlternateKey`, `HasPrincipalKey`), `migrationBuilder.Sql("""…""")`.
5. **TS-аналог:** миграции Prisma/Knex плюс сырой SQL для триггеров.
6. **Если убрать:** баг в коде или ручной SQL сможет записать несбалансированную запись или переписать историю.
7. **Вопрос техлида:** *Почему триггер отложенный?* Проводки вставляются по одной; после первой запись ещё не сбалансирована. Проверка должна идти в момент COMMIT, когда все проводки уже на месте.

## 5. Сверка (reconciliation)

**Файлы:** `src/LedgerCore.Infrastructure/Queries/LedgerReadStore.cs` (`ComputeReconciliationAsync`), `src/LedgerCore.Application/Reconciliation/ReconciliationService.cs`.

1. **Проблема:** кэшированный баланс (`balance_minor`) — это копия правды. Как убедиться, что он совпадает с журналом?
2. **Зачем:** журнал — источник правды, баланс — проекция для быстрых проверок.
3. **По шагам:** одна транзакция `REPEATABLE READ READ ONLY` (один снимок) → для каждого счёта сравнить кэш и сумму проводок → проверить Σдебет = Σкредит → найти несбалансированные записи → найти отрицательные кошельки. При расхождении: лог, метрика, аудит и **заморозка** кошелька. Кэш при этом **не** исправляется автоматически.
4. **C#:** `IsolationLevel.RepeatableRead`, `NpgsqlDataReader`, LINQ (`Where/Select/Distinct`).
5. **TS-аналог:** cron-задача с SQL-агрегатами.
6. **Если убрать:** ошибка или подделка кэша (например, `UPDATE … + 5000`) останется незамеченной, и «нарисованные» деньги можно будет потратить.
7. **Вопрос техлида:** *Почему не исправить кэш автоматически?* Это уничтожит улики бага или взлома. Сначала замораживаем и расследуем, потом исправляем осознанно.

## 6. Outbox и Worker

**Файлы:** `src/LedgerCore.Infrastructure/Outbox/OutboxDispatcher.cs`, `src/LedgerCore.Worker/Workers.cs`.

1. **Проблема:** уведомление о переводе нельзя потерять и нельзя отправить для перевода, который откатился.
2. **Зачем:** строка `outbox_messages` пишется **в той же транзакции**, что и перевод.
3. **По шагам:** воркер «арендует» пачку (`UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)`) → доставляет → помечает `processed_at`; при ошибке переносит `available_at` с экспоненциальной задержкой; после `MaxAttempts` отправляет в dead letter.
4. **C#:** `BackgroundService` (`ExecuteAsync` с циклом), `PeriodicTimer`, `IServiceScopeFactory` (новый scope на каждую итерацию).
5. **TS-аналог:** воркер BullMQ, только очередь хранится в той же PostgreSQL.
6. **Если убрать:** уведомления придётся отправлять прямо из запроса — с риском отправить за откатившийся перевод или потерять при падении.
7. **Вопрос техлида:** *Это exactly-once?* Нет, это **at-least-once**: если воркер упал после доставки, но до подтверждения, сообщение доставят ещё раз. Поэтому потребитель идемпотентен (`message_id` — первичный ключ). Это проверено настоящим убийством процесса воркера (`WorkerProcessTests`): 10 сообщений, 11 доставок, 10 уведомлений.

## 7. Api: безопасность и HTTP

**Файлы:** `src/LedgerCore.Api/Program.cs`, `Hosting/ApiSetup.cs`, `Hosting/EnvironmentGuards.cs`, `Security/AuthenticationSetup.cs`, `Endpoints/LedgerEndpoints.cs`, `Http/LedgerExceptionHandler.cs`.

1. **Проблема:** аутентификация, роли, строгий JSON, понятные коды ошибок, защита от случайного включения dev-функций в продакшене.
2. **По шагам:** `Program.cs` → `AddLedgerCoreApi` (регистрация сервисов) → `Build()` → `UseLedgerCoreApi`: сначала `StartupValidation.Validate` (откажется стартовать, если dev-токены или failure injection включены вне Development/Testing), потом middleware (correlation id → exceptions → auth → rate limit → authorization) и эндпоинты.
3. **C#:** Minimal APIs (`app.MapGroup("/api").MapPost("/transfers", CreateTransfer)`), атрибуты `[FromBody]`/`[FromHeader]`, `IOptions<T>`, extension methods (`this IServiceCollection services`).
4. **TS-аналог:** Express/Fastify-роутер + middleware; `IOptions<T>` ≈ типизированный config-модуль.
5. **Если убрать `StartupValidation`:** можно случайно задеплоить продакшен с известным dev-ключом подписи токенов.
6. **Вопросы техлида:**
   * *Почему 404, а не 403 при чтении чужого кошелька?* Чтобы нельзя было перебором выяснить, какие ID существуют.
   * *Может ли оператор перевести деньги клиента?* Нет: оператор может смотреть, сверять и делать reversal, но не дебетовать кошельки клиентов (разделение обязанностей).
